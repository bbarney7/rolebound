## Objective

Make connecting a model provider the first and nearly invisible step of Rolebound. On a fresh launch the server reports which AI accounts already exist on this computer, the UI offers each as one button, anyone not yet signed in gets a browser sign-in button, and pasting an API key stays available as the fallback. The ticket also closes two canary leftovers that live in the same code: the scoring picker that does not save, and Cursor transcripts written to `~/.cursor/projects`.

Click budget, asserted in e2e: a fresh user whose Cursor SDK login already exists reaches a complete readiness `connection` step in at most 2 user interactions after the page loads. The same assertion is made for a detected pi API key.

## Current state (verified in the PJR-23 worktree at `bfeed4f`)

- Connections live in workspace `settings.json` (`ui/server/applicationConfigStore.ts`, revision = sha256 of bytes, `ConfigRevisionConflictError` on mismatch), shape `Connection {id,label,provider,baseUrl?,api?,envKeyName?,email?,expiresAt?,cursorBackendUrl?}` (`ui/shared/config.ts:17-30`). `email`/`expiresAt`/`cursorBackendUrl` are allowed on cursor connections only (`validateConnection`, `ui/shared/config.ts:88-105`).
- The only secret store is `<root>/.pi-jobs/pi-agent/auth.json`, keyed `pi-jobs-<connectionId>`, entries `{type:"api_key",key}`. `readAuth` (`providerService.ts:35-48`) throws "credential store is malformed" on any other entry type. Mutations go through `withLock(<root>/.pi-jobs/pi-agent/.provider-store)` and an atomic temp+rename of the whole file (`providerService.ts:54-66`). `CredentialSource` is `"environment" | "app-store" | "none"` and is derived at read time (`publicConnection`, L57-61). `resolveCredential` (`ui/server/providers/providerService.ts:85-90`) returns `{connection, alias, source, apiKey?}`; `listModels` (L184) and `testConnection` (L201) read `.apiKey` and build provider catalog requests by hand (for example `x-api-key` against `https://api.anthropic.com/v1/models`, L151), while pi's own request adapter sends Anthropic OAuth tokens (`sk-ant-oat…`) as `Authorization: Bearer` plus the `claude-code-20250219`/`oauth-2025-04-20` beta headers (`pi-ai/dist/api/anthropic-messages.js:749-840`); `listRegistryModels` (L163) answers from the isolated registry without network.
- Provider kinds: `openai-compatible`, `cursor`, or any id in the generated `PROVIDER_CATALOG` (`ui/shared/providerCatalog.ts`, 34 entries in `PROVIDER_CATALOG` plus the hand-added `CURSOR_PROVIDER_ENTRY`, `{id,name,apiKeyEnv,scrubEnv}`). The generator (`scripts/gen-provider-catalog.mts`) keeps a provider only if it has `auth.apiKey`, so OAuth-only providers (`openai-codex`) are absent and `github-copilot` is denylisted. `ProviderKindSelect` lists the whole catalog.
- pi 1.0.4 (`@earendil-works/pi-coding-agent`): `ModelRuntime.create({credentials?: CredentialStore, authPath?, modelsPath?, refreshOnCreate?})`; `login(providerId,"oauth",interaction,options)` persists through the injected `CredentialStore`; `getAuth(providerId)` returns `AuthResult {auth: ModelAuth{apiKey?,headers?,baseUrl?}, source?}` after refreshing a stored `oauth` credential through `credentials.modify` when `now + 5 min >= expires`. `CredentialStore` is `{read, list, modify(providerId, fn), delete}` keyed by native provider id. The default file store (`AuthStorage`) locks `auth.json` itself with `proper-lockfile`, a different lock from Rolebound's `.provider-store`. `AuthInteraction` is `{signal?, prompt(AuthPrompt):Promise<string>, notify(AuthEvent)}` with events `auth_url|device_code|info|progress` and prompts `text|secret|manual_code|select`.
- pi-ai OAuth flows (`dist/auth/oauth/*.js`): `anthropic` (Claude Pro/Max; loopback `127.0.0.1:53692`, with a `manual_code` prompt raced against the callback so a busy port falls back to paste-a-code silently), `openai-codex` (ChatGPT Plus/Pro; loopback `localhost:1455` or device code, same silent fallback), `openai-chatgpt` (throws "Port 1455 is in use …" and requires `LoginOptions.getDeviceId()` returning a UUID), `github-copilot` (optional enterprise-domain `text` prompt, then `device_code`). No flow allows overriding its token endpoints; `anthropic`, `openai-codex`, `openai-chatgpt` and `openrouter` read `PI_OAUTH_CALLBACK_HOST` (default `127.0.0.1`) for the loopback host, and the only `LoginOptions` member is `getDeviceId`. No stored credential carries a refresh-token expiry. `ModelRuntime.login` persists the credential through the store **before** `synchronizeCredentialState`; a sync failure throws `CredentialSynchronizationError {providerId, operation, credential}` with the credential already stored. Copilot's stored credential carries `availableModelIds`, which pi uses to filter that account's models. Stored shape `{type:"oauth",access,refresh,expires /*epoch ms, 5 min margin already subtracted*/, ...extras}` (codex adds `accountId`, copilot adds `enterpriseUrl`, `availableModelIds`).

It does not set `CURSOR_DATA_DIR`; the Cursor SDK's `hn()` resolves `process.env.CURSOR_DATA_DIR ?? ~/.cursor` + `projects` and wrote 3 transcript files to `~/.cursor/projects/Users-brennen-rolebound-canary-pjr23` during the canary.

## Decisions

- **D1. Detect broadly; adopt directly only what does not rotate.** Detection reports presence, source, account label and expiry for six sources (table in T4). The single "Use this" button does one of two things depending on the source: **adopt** (create the connection and defaults with no further input) for the Cursor SDK store, pi global `api_key` entries (key copied into the app store) and environment keys (nothing copied; `source: "environment"`); or **sign in** (create the connection and immediately start Rolebound's own OAuth login for that provider, then set the same defaults on success) for Claude Code, Codex, GitHub CLI and pi `oauth` entries. Those tokens rotate on refresh, so copying one would sign the user out of Claude Code or Codex at the next refresh; the ticket's AC1 is amended to say exactly this. Q1 asks the owner to confirm or to accept the trade-off for a zero-click path; if the owner chooses zero-click, D1 changes to adapters that refresh and write back into the source store, and T4 grows by one task.
- **D2. OAuth providers come from pi, through `ModelRuntime.login`, and only three are exposed.** The catalog gains an `auth` block generated from pi: `{apiKey?: {env}, oauth?: {name, loginLabel?, isSubscription?}}` and a `roles: ("agent"|"scoring")[]` capability list (`cursor` agent-only, `typesafe` scoring-only, everything else both). OAuth is emitted only for an allow-list: `anthropic` (Claude Pro/Max), `openai-codex` (ChatGPT Plus/Pro) and `github-copilot`; `openai`'s ChatGPT flow is not exposed (it would duplicate `openai-codex` and needs `getDeviceId`), and the other OAuth-capable providers keep API-key only. `openai-codex` is added to the catalog as OAuth-only; `github-copilot` leaves the denylist. Because pi's anthropic and codex flows fall back to a `manual_code` prompt when their loopback port is busy, there is no `LOGIN_PORT_BUSY` code; the generic prompt UI shows the paste-a-code field.
- **D3. One credential store, one lock.** `ui/server/providers/connectionCredentialStore.ts` implements pi's `CredentialStore` for **one connection**: `read/list/modify/delete(providerId)` map the native provider id to the alias `pi-jobs-<connectionId>` in the app-store `auth.json`, and every write runs inside the existing `withLock(.provider-store)` + temp/rename writer that `providerService` already uses. Two consequences are designed in: pi performs the OAuth refresh network call inside `modify` (15 s timeout) while the lock is held, and other writers give up after the ~12 s retry budget, so `resolveCredential` refreshes **before** taking any Rolebound write path and connection edits during a refresh surface the existing lock error rather than corrupting the file; and `withFileLock` is not re-entrant (`LockReentryError`), so code that already holds the lock calls lock-free inner helpers (`*Unlocked` variants extracted from `createConnection`/`updateSelections`/`store.modify`). `ModelRuntime.create({credentials: store, modelsPath: null, refreshOnCreate: false})` is used for login, `getAuth` (refresh) and `checkAuth`. pi's own `AuthStorage` is never pointed at the app store, so there are no competing lockers. `auth.json` entries become pi `Credential` (`api_key | oauth`); `readAuth` accepts both; `CredentialSource` gains `"oauth"`; `email`/`expiresAt` metadata are allowed on cursor and OAuth-capable providers.
- **D4. Credential resolution returns pi `ModelAuth`, and OAuth connections never use Rolebound's hand-built catalog requests.** `CredentialResolution` becomes `{connection, alias, source, apiKey?, credential?: Credential, auth?: ModelAuth}`; `apiKey` is kept and always equals `auth.apiKey` (for `api_key`, env and `oauth` alike) so the existing readers in `runConfig.ts` (L308, L329-352), `providerService.test.ts` (L17-22, L67) and the ported Cursor tests keep compiling and passing. For `api_key` and env keys `auth = {apiKey}`; for `oauth` it is `runtime.getAuth(providerId).auth` (refresh happens here, persisted through D3's store) and the refreshed `credential` is re-read from the store. `prepareAgentRun` and the scorer check consume `credential`/`auth`. For `source: "oauth"`, `listModels` answers from `listRegistryModels` (filtered by Copilot's `availableModelIds` when present) and `testConnection` succeeds when `getAuth` returns without a refresh error and the selected model exists in the registry; no manual HTTP probe is made, because only pi's request adapter knows the OAuth header rules (Bearer + beta headers for Anthropic, Copilot's base URL and filters). Real OAuth traffic happens only inside the pi child at run time (spike 4). Precedence: a stored `oauth` credential beats an ambient env key (matching pi); stored `api_key` entries keep today's env-first order in both `resolveCredential` and `publicConnection`, so `providerService.test.ts` L22 and L64-69 stay as they are.
- **D5. Per-run OAuth: refresh before, write back after.** `prepareAgentRun` writes the refreshed `oauth` credential into the per-run `auth.json` under the native provider id (the child runs pi's `AuthStorage` on that private file, which is fine). `runManager` registers a `beforeCleanup` hook: on `exit`, `abort` and server shutdown drain it reads `<runDir>/pi-agent/auth.json` and, for each `oauth` entry whose `expires` is later than the stored one, calls `store.modify` to write it back. A hard kill between a child refresh and write-back loses the rotated token; readiness then shows `CREDENTIAL_EXPIRED` → "Sign in again" (D7). Documented as residual. Two different OAuth connections of the same provider cannot both be selected (agent and scorer): the per-run alias mechanism (`pi-jobs-<id>` in `models.json`) does not inherit the built-in provider's OAuth adapter, so the server rejects that combination with 422 `CONFIG_INVALID` after `readAuth` (credential type is only known from `auth.json`, so the check lives in `updateSelections`, `finalizeDefaults` and `prepareAgentRun`, never in the pure `validateSelection`/`validateSettings` that run on every settings read) ("use the same connection for scoring, or an API-key connection") and readiness reports the same code. When one selected connection of a provider is OAuth and the other is API-key, `runModelProviderKey` gives the native provider id to the OAuth connection (whichever role it has) and aliases the API-key one, because only the native id carries pi's OAuth adapter; both role orderings are tested.
- **D6. One login-session API for every browser sign-in, plus provider-level entry points.** `ui/server/providers/loginSessions.ts` generalises the Cursor `sessions`/`settled` maps. Routes: `POST /api/providers/login {provider}` (creates or reuses a credential-less connection of that provider, starts the session, returns `{connectionId, session}`), `POST|GET|DELETE /api/connections/:id/login`, `POST /api/connections/:id/login/answer {promptId, value}`. Session state `{status: pending|succeeded|cancelled|failed|interrupted, authUrl?, deviceCode?: {userCode, verificationUri, expiresAt}, prompt?: {id, type, message, placeholder?, options?}, info?: string, error?: {code, message}}`. Bridge rules: `notify(auth_url)` sets `authUrl`; `device_code` sets `deviceCode`; `info|progress` set `info`; `prompt()` parks a promise under a fresh `promptId` and subscribes to the prompt's own `signal` (pi aborts it when the loopback callback wins): on abort the parked promise rejects, the prompt is removed from the state and a later answer gets 409 `PROMPT_STALE`; the first `select` prompt is auto-answered with the option whose id or label contains "browser", otherwise surfaced; Copilot's leading `text` prompt (GitHub Enterprise domain) is auto-answered with `""` (github.com) so the popup goes straight to `verificationUri`, and a secondary "GitHub Enterprise…" link on the button starts the session with `{enterpriseDomain}` instead; a `select` answer must be one of the offered option ids, else 422 `PROMPT_INVALID`; `answer` with an unknown or already-answered `promptId` → 409 `PROMPT_STALE`; `cancel` aborts the controller, rejects any parked prompt, status `cancelled`; settled sessions are kept 10 minutes then dropped; after a restart `GET` returns `interrupted`. On success the returned `Credential` is written through D3's store, `email`/`expiresAt` are recorded when the credential or `checkAuth` exposes them, and defaults are finalised (D8). A `CredentialSynchronizationError` whose `credential` is set means pi already persisted the credential: the session is treated as succeeded and finalisation continues (the sync failure is logged as `info`). Any other failure happens before persistence, so the credential-less connection remains with `source: "none"` and is reused by the next attempt. Auto-created connections (adopt, provider login, the second Jev connection) are labelled inside the locked transaction as the catalog name plus the account when known ("Cursor · dev@example.com", "Claude Pro/Max"), with a numeric suffix (" 2", " 3") when `createConnection`'s case-insensitive label uniqueness check would otherwise 422. `POST /api/providers/login` accepts `{provider, detectionId?, enterpriseDomain?}` (`enterpriseDomain` only valid for `github-copilot`, 422 otherwise; `POST /api/connections/:id/login` takes the same optional field): with a `detectionId` it validates the id against current detection, persists that origin (D9) on the connection and returns `{connectionId, session}` in one call, so a detected sign-in source is also a single "Use this" click. The server pins `PI_OAUTH_CALLBACK_HOST=127.0.0.1` in its own `process.env` at startup (`ui/server/index.ts`; pi reads it when an OAuth flow module is first imported, which happens lazily at the first login, so server startup is early enough and no import reordering is needed) and strips it from the run child env like other scrub names; tests and the fresh e2e set it explicitly. Cursor dispatches inside the same module to the SDK login (`startCursorLogin` body with `openBrowser: false`; the login URL reaches the UI as `authUrl` like every other flow) and the existing-login import becomes `POST /api/connections/:id/login {mode: "import"}` for cursor connections (opens `FileCredentialStore(<home>/.cursor/sdk/auth.json)` from `deps.home`, same expired / not-signed-in / non-production-backend responses as today, so the "Use my existing Cursor login" button on an existing card survives) while a fresh user reaches the same code through `POST /api/providers/adopt {detectionId: "cursor-sdk:cursor[:email]"}`; the `cursor-login`/`cursor-import` routes are removed.
- **D7. Readiness treats access-token expiry as refreshable.** For `source: "oauth"`: no blocker from `expiresAt` alone. `CREDENTIAL_EXPIRED` fires only when the connection carries `refreshFailedAt` (set by `resolveCredential` when `getAuth` throws `OAuth refresh failed`, cleared by a successful login or refresh). No pi credential exposes a refresh-token expiry, so there is no OAuth `LOGIN_EXPIRING` warning; `CURSOR_LOGIN_EXPIRING`/cursor `CREDENTIAL_EXPIRED` unchanged.
- **D8. Defaults are chosen without prompts, as one transaction.** `finalizeDefaults(root, connectionId, detected)` runs under the `.provider-store` lock (using the lock-free inner helpers, never the public `createConnection`, which would re-enter; `updateSelections` takes no lock, only the revision check, so `finalizeDefaults` reuses its `validateSelection` + revision write directly) with a `settings.json` revision retry loop and sets: agent = this connection + `defaultModels.agent[provider]` if the provider has the `agent` role; scoring = (a) Jev if a TypeSafe or OpenRouter credential is available (a detected TypeSafe/OpenRouter key is adopted as a second connection in the same transaction), else (b) inherit (`scoring: null`) when the agent provider has the `scoring` role, else (c) the first other detected API-key provider with `defaultModels.scoring[provider]`, else (d) `scoring: null` and the existing `SCORING_MODEL_MISSING` readiness explains. A TypeSafe-only detection configures scoring only. A Cursor-only adoption therefore ends with `scoring: null` and `SCORING_MODEL_MISSING` (Cursor is agent-only; the ticket's AC2 is amended to say so). `defaultModels.ts` holds explicit agent and scoring ids for the popular providers (`anthropic`, `openai`, `openai-codex`, `github-copilot`, `google`, `openrouter`, `cursor`) and a deterministic fallback for every other agent-capable catalog provider: the first model in the isolated registry's order for that provider whose `input` includes `text` and which is not reasoning-only or embedding-only; for Copilot the choice is made after login from the models that survive the credential's `availableModelIds` filter, in the same preference order. Tests: explicit ids validated per kind (native through the isolated `ModelRuntime`, cursor through `isKnownCursorPiModelId`, Jev through `jevModels.ts`) and a catalog-wide test proving every agent-capable catalog provider yields a registry-valid agent selection, plus a Copilot fixture where the global default is not in `availableModelIds`. `composer-2.5` is the cursor default (owner's choice).
- **D9. Adoption is idempotent through a stored, non-secret origin.** `Connection.origin?: {kind: DetectedKind, account?: string}` is written on adopt/sign-in; a detection id is `<kind>:<provider>[:<account>]`; adopting an id whose origin already exists returns that connection (200) instead of creating another; two concurrent adopts of the same id serialise on the lock and yield one connection (tested).
- **D10. UI: one new component, existing cards untouched.** `ui/src/ProviderSetup.tsx` owns only the "add a connection" surface: detected accounts (one button each, action label "Use this"), then "Sign in with Claude / ChatGPT / GitHub Copilot / Cursor" for providers not detected, then a collapsed "Paste a key instead" that reuses the existing form with `ProviderKindSelect` filtered to `auth.apiKey` providers. Existing connection cards (Stamp, Test, Remove, status line) and `ConnectionSelections` stay where they are in `SettingsPanel.tsx` and `SetupView.tsx`; `CursorConnectionAuth.tsx` is replaced by a provider-agnostic `LoginButton.tsx` inside the card. Cursor copy says "Cursor account" and "bills to your Cursor plan", never "API key". The server rejects an `apiKey` on an OAuth-only provider with 422 `CONFIG_INVALID`.
- **D11. Scoring picker fix.** Changing the scoring connection clears `scoreModel`, then auto-fills it when the connection has exactly one scoring-eligible model (TypeSafe → `jev-latest`) or when `defaultModels.scoring[provider]` exists; the server error is shown inline and the `[value]` effect only resets fields the user has not edited since the last save. First React component tests are added (jsdom + `@testing-library/react` in `ui` dev deps).
- **D12. Cursor transcript isolation is a run-config env rule.** When `loadsCursor`, `prepareAgentRun` sets `CURSOR_DATA_DIR=<runDir>/cursor-data` (0700) and always deletes an inherited `CURSOR_DATA_DIR`; `cleanup` removes it with the run dir. Verified once against the real SDK in the canary and logged; CI unit-tests the env only.
- **D13. Transcript redaction knows OAuth.** `createSecretsReader` collects `access` and `refresh` from `oauth` records, and `runManager` registers the active run's `pi-agent/auth.json` as an extra source so rotated tokens are redacted too.
- **D14. Demo mode is synthetic.** `GET /api/providers/detected` returns `[]` in demo mode; `POST /api/providers/*` and the login routes return 409 `DEMO_DISABLED` through `demoExternalBlock`.
- **D15. Minimal safety, per owner.** No new consent steps, warnings or caps. Detection reads presence and metadata only and never prints tokens; `SECURITY.md`'s one sentence is extended to say Rolebound reads these files to offer sign-in shortcuts.
- **D16. Tests never touch the real home or the developer's keys.** Detection takes injected `{home, env, platform, keychainProbe, ghProbe}`, threaded through `createApp` options so route tests cannot reach the real home; the fresh e2e strips every generated scrub name (reusing `loadScrubEnvNames`/`buildChildEnv`) and seeds fixture credential files under its isolated `HOME` with the `FIXTURE-SECRET-do-not-leak` sentinel.

## Spike (T1, half a day, before anything else)

Record results under "Spike results" in this plan:

1. `ModelRuntime.create({credentials: <in-memory ConnectionCredentialStore>})` then `login("anthropic","oauth", stubInteraction)`: confirm the event order (`select` → auto browser → `auth_url` → `manual_code` prompt raced with the callback), and that the returned credential is written through the injected store under the native id. Repeat for `openai-codex` (device-code branch) and `github-copilot` (text prompt → `device_code`). Do not complete a real login.
2. With `globalThis.fetch` stubbed in vitest, drive the anthropic flow end to end: read `authUrl` from the session, POST a fake code to the loopback callback (or answer the `manual_code` prompt), serve a fake token response, assert the stored `oauth` credential. This becomes the pattern for T3's per-provider tests; if the callback cannot be driven for a provider, that provider's test answers the `manual_code`/`device_code` path instead and the plan says so.
3. `getAuth("anthropic")` on a stored `oauth` entry with `expires` in the past hits the stubbed refresh endpoint and persists through `store.modify`; assert the refreshed credential is what `read` returns afterwards.
4. A per-run `auth.json` containing an `oauth` entry under the native provider id is accepted by the pi RPC child (runtime-smoke pattern with a fake token and a loopback model server). There is no generic fallback: converting an OAuth token into an `api_key` entry would not work for `openai-codex` (no API-key auth) and would skip pi's OAuth headers. If the child rejects the entry, the spike blocks the ticket (`syntaur block`): log the exact failure and raise a question; the ways forward are a compatible per-run mechanism, a pi dependency change, or an explicit ticket amendment by the owner. Dropping a provider silently is not an outcome, because AC3 names Claude, ChatGPT and Copilot.
5. Default model ids for `anthropic`, `openai`, `openai-codex`, `github-copilot`, `google`, `openrouter` exist in the isolated registry; `composer-2.5` passes `isKnownCursorPiModelId`.
6. `CURSOR_DATA_DIR` in the canary (`~/rolebound-canary-pjr23`, launcher `scratchpad/p23/canary-start.sh`): one status run + "READY" prompt; `~/.cursor/projects/Users-brennen-rolebound-canary-pjr23` stays at 3 jsonl files and new transcripts appear under the run dir. If the SDK still writes to `homedir()` for some paths, record which and keep D12 as best effort with the leak documented.
